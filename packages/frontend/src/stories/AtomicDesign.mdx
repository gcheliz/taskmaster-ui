# Atomic Design Architecture

TaskMaster UI follows the Atomic Design methodology created by Brad Frost, organizing our components into a clear hierarchy that promotes consistency, reusability, and maintainability.

## What is Atomic Design?

Atomic Design is a methodology that breaks user interfaces down into their basic building blocks and works up from there to create a design system. Think of it as chemistry - we combine simple atoms to create molecules, then combine molecules to create organisms.

## Our Component Hierarchy

### ⚛️ Atoms

**Basic building blocks of our interface**

Atoms are the smallest functional units in our design system. They cannot be broken down further without losing their meaning.

**Examples in our system:**

- `Button` - All button variants and states
- `Input` - Form input fields
- `Label` - Text labels for form elements
- `Icon` - SVG icons and iconography
- `Badge` - Status and notification badges
- `Card` - Basic card container
- `Checkbox` - Checkbox input elements
- `Radio` - Radio button elements
- `Select` - Dropdown selection
- `Textarea` - Multi-line text input
- `Toggle` - Switch/toggle elements
- `Spinner` - Loading indicators

**Key characteristics:**

- Single responsibility
- No dependencies on other components
- Highly reusable
- Consistent styling and behavior

### 🧬 Molecules

**Simple groups of atoms functioning together**

Molecules are relatively simple groups of UI elements functioning together as a unit. They're generally made up of 2-4 atoms and have a specific purpose.

**Examples in our system:**

- `FormField` - Label + Input + validation
- `Modal` - Overlay container with content
- `Dropdown` - Trigger + menu items
- `Pagination` - Navigation controls
- `Tabs` - Tab navigation system
- `Toast` - Notification messages
- `Card` - Enhanced card with header/footer
- `Alert` - Status messages with icons
- `SearchField` - Input with search functionality
- `KanbanColumn` - Task board column
- `KanbanTaskCard` - Individual task cards
- `ProjectHealthIndicator` - Status visualization
- `QuickActionCard` - Action buttons with descriptions
- `StatisticsGrid` - Metrics display
- `TimelineItem` - Event timeline entries

**Key characteristics:**

- Composed of 2-4 atoms
- Single, clear purpose
- Self-contained functionality
- Reusable across contexts

### 🦠 Organisms

**Complex components composed of molecules and atoms**

Organisms are more complex UI components composed of groups of molecules and/or atoms. These form distinct sections of an interface.

**Examples in our system:**

- `ActivityTimeline` - Complete timeline with multiple items
- `KanbanBoard` - Full task board with columns and cards
- `QuickActionsGrid` - Grid of action cards
- `ResponsiveStatsGrid` - Comprehensive statistics display
- `Navigation` - Main navigation system
- `Header` - Application header with user controls
- `Sidebar` - Navigation sidebar with menu items
- `Footer` - Application footer with links

**Key characteristics:**

- Made up of molecules and atoms
- Form distinct interface sections
- Handle complex interactions
- May have their own state management

## Development Guidelines

### When Building Atoms

- ✅ **Do**: Focus on single responsibility
- ✅ **Do**: Include all possible variants and states
- ✅ **Do**: Provide comprehensive prop documentation
- ✅ **Do**: Include accessibility attributes
- ❌ **Don't**: Include business logic
- ❌ **Don't**: Make assumptions about usage context

### When Building Molecules

- ✅ **Do**: Compose existing atoms when possible
- ✅ **Do**: Handle related state management
- ✅ **Do**: Include validation and error states
- ✅ **Do**: Document all composition patterns
- ❌ **Don't**: Create new atoms inside molecules
- ❌ **Don't**: Make molecules too complex (max 4 atoms)

### When Building Organisms

- ✅ **Do**: Use existing molecules and atoms
- ✅ **Do**: Handle complex interactions and workflows
- ✅ **Do**: Include comprehensive examples
- ✅ **Do**: Document integration requirements
- ❌ **Don't**: Include page-specific business logic
- ❌ **Don't**: Hardcode data or API calls

## Story Requirements

Every component must include comprehensive Storybook stories with:

### Required Stories

- **Default** - Basic usage example
- **All Variants** - Every visual variant
- **All Sizes** - Every size option (if applicable)
- **Interactive States** - Hover, focus, active, disabled
- **Accessibility Test** - Keyboard navigation and screen readers

### Optional Stories

- **Dark Theme** - Dark mode variants (if applicable)
- **Error States** - Error handling and validation
- **Loading States** - Async state management
- **Complex Examples** - Real-world usage patterns
- **Micro-interactions** - Animation and transition showcases

## Accessibility Standards

All components must meet WCAG 2.1 AA compliance:

- ✅ **Color Contrast**: Minimum 4.5:1 for normal text, 3:1 for large text
- ✅ **Keyboard Navigation**: All interactive elements keyboard accessible
- ✅ **Focus Management**: Clear focus indicators and logical tab order
- ✅ **Screen Readers**: Proper ARIA labels and semantic HTML
- ✅ **Motion**: Respect `prefers-reduced-motion` settings

## Testing Strategy

Each component level has specific testing requirements:

### Atoms

- Unit tests for all props and variants
- Accessibility tests (axe-core)
- Visual regression tests
- Interaction tests

### Molecules

- Integration tests for atom composition
- Form validation tests (if applicable)
- User workflow tests
- State management tests

### Organisms

- End-to-end workflow tests
- Performance tests for complex interactions
- Cross-browser compatibility tests
- Responsive design tests

## Naming Conventions

### Component Names

- Use PascalCase: `FormField`, `KanbanBoard`
- Be descriptive but concise
- Avoid abbreviations: `Button` not `Btn`

### Story Names

- Use descriptive titles: `"With Left Icon"` not `"Icon"`
- Group related stories: `"Interactive States"`
- Use consistent naming across components

### Props

- Use camelCase: `onClick`, `isDisabled`
- Boolean props should start with `is`, `has`, or `can`
- Event handlers should start with `on`

## Performance Guidelines

- **Bundle Size**: Keep atoms < 5KB, molecules < 15KB
- **Render Performance**: Use React.memo for expensive computations
- **Tree Shaking**: Export components individually
- **Code Splitting**: Large organisms should support lazy loading

## Migration Path

When refactoring existing components to atomic design:

1. **Audit**: Identify existing components and their dependencies
2. **Extract**: Pull out reusable atoms from complex components
3. **Compose**: Rebuild molecules using extracted atoms
4. **Consolidate**: Combine molecules into organisms
5. **Document**: Create comprehensive Storybook stories
6. **Test**: Ensure functionality and accessibility
7. **Deploy**: Gradually replace old components

## Benefits

### For Developers

- **Consistency**: Shared component library reduces code duplication
- **Maintainability**: Changes to atoms propagate through the system
- **Testability**: Isolated components are easier to test
- **Collaboration**: Clear structure improves team communication

### For Designers

- **System Thinking**: Encourages systematic approach to design
- **Reusability**: Design patterns can be reused across products
- **Scalability**: New features built from existing components
- **Documentation**: Living style guide with interactive examples

### For Users

- **Consistency**: Familiar patterns across the application
- **Performance**: Optimized, reusable components
- **Accessibility**: Built-in accessibility features
- **Reliability**: Well-tested components reduce bugs
